# 阅读器标准样式原位换肤：独立只读审核任务书

日期：2026-09-28。状态：待执行。本文不表示施工或审核已经通过。

## 1. 审核对象与角色

审核 [一次完成施工任务书](reader-shadcn-default-inplace-plan.md) 约定的整批产品修改。U01–U10 仅是初始工作分组，不是项目界面总数或检查上限。执行模型一次完成实际盘点清单中的本轮施工与检查后，用户或调度者安排一个新的独立审核对话；不是每个页面做一次审核。

审核模型只读：不修改源码、样式、测试、文档、tasks.md、状态或提交，不修复发现的问题，不创建/委派对话或子代理，不使用 worktree。只输出结论与必要发现。

默认读取现有证据，不重复跑全套命令。`npm run build` 会写 dist，部分测试会写文件或服务数据，不能因为命令名叫 verify 就在只读审核中直接运行。必要疑点优先检查源码与现有日志；如确需独立浏览器复核，使用临时隔离上下文及合成/模拟数据，确认不会写真实 Host、用户设置或仓库。缺少安全复核环境则报告对应证据缺口，不自行创建持久化环境。

## 2. 开场读取顺序

1. AGENTS.md 与施工任务书，尤其第 1 节固定设计、第 2 节范围、第 5 节验收和异常处理表。
2. `docs/design/reader-shadcn-default-inplace-handoff.md`，取得起始/结束 HEAD、本轮文件、实际界面/入口/状态清单、U/V 映射及真实与模拟证据范围。只有 U01–U10 概览勾选表不算完整盘点。
3. 当前 Git 状态和本轮 diff。若未提交，相对 HEAD 的 diff 含开场 Host/SRS 等既有改动，需按开场记录区分；不得把整个工作区差异当成本项修改。
4. 执行交接引用的截图/日志和实际产品源码。截图说明可以帮助定位，但不能只凭“PASS”字样相信布局或功能已经验证。

缺交接、基点或关键证据时先说明具体缺什么。不要要求新建统一报告生成器、SHA-256 包、录像、全浏览器矩阵或证据文本解析器。

## 3. 固定审核标准

每条填写 PASS / FAIL / NOT_VERIFIED。未验证不是通过；不是因为文档有勾选就判通过。

## 4. 优先复核的具体位置

先检查盘点是否遗漏，再核对本轮差异及低成本疑点，不做新的全仓库架构审计。

入口完整性核对必须独立进行：从 index.html/main.js/App.vue 的当前加载链和实际按钮/菜单/快捷键、动态组件、Teleport、原生窗口创建点，对照执行清单。不能仅因为清单自称完整就接受。发现遗漏时指出具体入口路径、所属对象和适用的既定标准；不要要求重建清单工具或重新设计所有界面。一个界面多入口不重复计数，状态也不计为新页面。

施工负责按实际清单逐项打开；审核核对全表记录，再对遗漏疑点、共享规则风险和关键结果进行低成本抽查，不机械重跑全部旅程。记录源码可达但入口受阻、仅隔离挂载、历史不可达等事实，不能将三者混为“已从正常入口验收”。

1. `src/main.js` 与 `src/App.vue`：原生 size 参数、三个 Teleport 学习按钮、主题图标；确认脚本顺序、事件和 Teleport 目标没动。
2. `styles.css` 的 `reader-footprint`、按钮旧固定宽高及控制区玻璃伪元素：核对新配方是否真正生效，是否误删 layout 规则。
3. `src/styles/workflow-ui.css` 的 reader/workflow/theme state、浅色默认、自定义映射、dark variant；`learning-ui.css` 的浅色固定范围。
4. `YouTubeWorkflowPanel.vue` 主界面、quality footer 和 material notice，检查独立 Teleport 表面及 pending。
5. 两个原生解释/词汇模块的创建调用；`style-editor.js` 当前可达弹窗；不要漏掉第二个窗口的关闭/footer。
6. `PassagePreviewPage.vue` 的原生导航与完成页；SettingsDialog 的 number；快捷键弹窗的真实 DOM 焦点。
7. `SrsReviewPage.vue` footer 的 v-if、actions、disabled、tone、handleRating 与 revealAnswer；学习服务不应被样式任务修改。
8. `LearningPageLoadNotice.vue` 的 emits/条件分支和 Tailwind 精确扫描范围。
9. 已有尺寸断言更新：vocabulary-preview-ui 的 icon-sm、annotation-backfill 的 size-8；仍需看到行为断言保留。
10. 若用 `verify:youtube-workflow-panel-behavior`，检查显式 READ_WEB_URL。不得把默认 5173 的历史实例当作本轮验收；verify:vite 也要确认未误复用旧服务。
11. 检查 CSS 来源/处置表能否对应实际界面清单，尤其同组中的多个窗口和 tab；按实际删除的规则抽查残余消费者、动态状态和后测。区分 Coverage 使用记录与声明最终胜出；不能以首页未命中、规则被划掉、总行数下降或使用率上升认定清理正确。

Coverage 因工具限制未采集但已如实记录，且逐界面实际样式检查、删除依据和后测充分时，不单凭缺少 Coverage 百分比判 FAIL。没有消费者确认的疑似无用 CSS 保留是允许的；不得要求所有旧 CSS 清零或额外扩大全站审计。若关键删除没有足够依据，应按实际证据缺口或具体回归给出 NOT_VERIFIED/FAIL。

## 5. 如何处理发现和证据不足

- 每个要求修复的发现必须对应 A01–A10，或说明具体 P0–P2 产品/数据/回退故障及触发路径；不能只用个人审美判错。
- 发现格式：`[P级别][A编号] 标题 → 文件及行号 → 触发条件 → 当前结果/要求结果 → 最小修正方向`。
- 尚未确定的风险写成“未验证/疑点”，说明缺哪项证据；不能当作已经复现的产品 bug。
- 纯历史失败注明与本轮无关。若某个历史问题实际阻断本次必要验收，报告该项 NOT_VERIFIED；不自动扩成后台维修或全套清绿。
- 一条问题只要求直接修复和对应复测；已有有效证据可复用。不能要求为了截图漂亮清理真实数据或更改配置。
- 没有实际缺陷不要硬凑发现，允许结论 PASS。

## 6. 输出格式和结束条件

最终报告直接输出到对话，禁止写入仓库：

```text
结论：PASS / FAIL / NOT_VERIFIED
审核范围：本轮文件与基点；是否为未提交差异。
入口覆盖：实际界面/子项数量与分类；遗漏、受阻、未检查项；只报告有依据的范围，不写“项目仅有10个界面”。
标准表：A01–A10，各自状态和一句证据/原因。
发现：按严重程度列出，若无则写“无阻塞发现”。
未验证项/历史限制：具体列出；不要把模拟说成真实持久化。
复核方式：读取哪些证据、独立复核哪些内容。
```

- PASS：A01–A10 的适用要求有充分证据，实际入口清单无已发现的漏项、必要检查无未解释缺口，无本轮实际阻塞缺陷。专用保留区的分类与共享影响已交代即可，不要求证明其全功能通过。
- FAIL：有已确认的验收不符合或具体产品缺陷。
- NOT_VERIFIED：没有足够证据给出通过/失败，例如真实主阅读页始终未能取得或无法确定展示的是当前产物；列出最小补充内容。
- 若同时有确认缺陷和证据不足，结论 FAIL，另列未验证项。

技术 PASS 后，由用户实际查看是否接受视觉效果，不让审核模型代替用户喜好。正式日常替换仍属于后续显式操作。

如确需修复，由用户/调度者安排针对发现的修复，修复后只复核相关项。遵守同任务连续两轮修复/复审失败后停止自动循环规则；不自动创建第三轮任务，也不修改任务边界。
