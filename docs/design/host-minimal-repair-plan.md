## 3. HOST-01：保存版本冲突的有限恢复

### 目标和验收口径

一个后台写入在读快照与提交之间抢先完成时，本次学习操作能基于新快照再计算并保存；不丢另一方的数据，不产生重复事件／评分。持续竞争能明确失败；未知保存结果不盲目重发。

### 顺序步骤

1. 建立一个小型回归：两套实际 Owner 集成实例共享同一存储；A 读取 revision N 后，B 完成一笔写入使 revision 变成 N+1，再让 A 提交。确认旧实现报上述 `REVISION_CONFLICT`。不要用只有字符串断言的检查代替这个次序。
2. 改动优先限定在 `createOwnerLearningRunner`，同时覆盖单命令和现有 batch session。只有 Host 明确表示本次因版本变化未提交，才重新查询快照、创建新的内存事务、重新执行本次业务计算。
3. 初始提交加最多两次重算，共最多三次。持续冲突直接返回清晰错误；不增加无限循环、长时间轮询或全局写入队列。读取失败、业务校验失败、Host 未就绪和结果未知不进入这段冲突恢复。
4. 区分两种身份：业务 command ID 保持不变，用来防止重复业务操作；已确认冲突后重新计算的 HTTP 提交具有新的 expectedRevision／内容，应使用与该次版本及内容绑定的提交身份。不能复用已绑定旧请求的 transport idempotency key，也不能通过随机业务 ID 跳过业务去重。
5. 保留现有未知提交结果的回执查询路径。只有匹配本次实际请求的成功回执才算保存完成；查不到、内容不匹配或仍未知，就向调用方报告未确认，不自行生成新 key 再写一遍。只补本项直接涉及的匹配条件，不扩大成新的回执管理系统。
6. 核对被重算 callback 只操作事务中的数据；外部写入／网络副作用不能随 callback 重放。同一次业务操作的 `recorded_at`、事件 ID、发生时间应在重算之间稳定。例如评分 `recorded_at` 当前在 callback 内取时，可在进入事务前取一次。批处理同样按逻辑命令保留时间，不随循环重新生成。
7. 保留当前错误的 code/outcome，给最终错误文本增加可辨识原因，例如 `REVISION_CONFLICT`。不把版本冲突继续写成 Host 离线，不打印凭据或整份业务数据。

### 必要检查

- 单命令和批处理各发生一次确定性竞争后，两个写入者的数据都保留。
- 重复执行同一已完成业务命令，不新增评分、事件或业务回执。
- 持续冲突三次即退出；未知结果不重复发送 mutation。
- 同一 command ID 改变业务内容仍被拒绝，不把业务 ID 冲突当成 CAS 自动恢复。
- 用实际 Python `VocabularySrsOwner` 和少量临时合成记录，验证 revision、请求身份、重新加载后的内容；不要求启动完整 UI-Dev 或做全六域迁移。

既有针对性命令：`npm run verify:windows-owner-vocabulary-srs`、`npm run verify:vocabulary-acquisition-service`、`npm run verify:vocabulary-article-acquisition`、`npm run verify:srs-review`。修改评分路径时补 `npm run verify:srs-review-ui-v2`。新回归尽量放既有合适位置；若确需独立脚本，保持短小并只维护项目已有登记项。

### 简单修法与交接

若重算导致重复事件，先固定业务身份和时间；若提交 key 仍冲突，检查它是否与实际 revision／内容一致；若 batch callback 含外部副作用，先把该副作用移出重算部分，不扩成全站事务改造。

交接只写：复现次序、改动文件、重算边界、检查结果、仍未验证的入口。通过即进入 HOST-02。

## 4. HOST-02：预习入口的命令 ID 问题，复现才修

### 目标和验收口径

正常预习首次打开、关闭后重开及刷新后重开，不因同一业务命令对应不同内容而被阻断。只有旧测试数据触发时单列历史问题；不要求为了本轮完成而清洗旧库。

### 顺序步骤

1. 使用两个合成词，从当前实际预习入口走一次注册、关闭重开和刷新。可复用项目已有浏览器运行方式；不要为了 Node 直接导入 Vue／JSON 的便利修改产品模块导入。
2. 若没有复现，记录“本轮合成路径未复现”，本项结束。不能据此声称旧数据已修复，也不凭猜测改命令生成逻辑。
3. 若复现，记录具体 command ID、command type 和两个 payload 的差异字段，例如 created_at、target sense、context ID。只记录定位所需字段，不导出整个词库。先分清这是业务 `IDEMPOTENCY_CONFLICT`，还是 Host 提交层的版本冲突。
4. 定位最早出现差异的调用方：若是同一操作重开，复用已持久化的身份和原始时间；若确实是新的用户操作，使用其真实业务身份。若前几个步骤已经保存、最后一步失败，应从未完成步骤继续，不能从头重造已完成命令。
5. 修改范围优先是 `passage-preview-acquisition.js` 或 `vocabulary-service.js` 的局部身份／恢复逻辑。保持 `executeWithRowPort` 的内容指纹保护，不删除回执、不重置 Owner，也不把所有 command ID 改成随机值。

### 必要检查

- 原复现路径不再报错，重开使用相同 learning unit。
- 成功步骤没有重复执行；刷新后仍能读回已有记录。
- 对同一 ID 故意传入另一份内容仍明确报错，确保真正的冲突没有被吞掉。
- 若修改预习获取流程，运行 `npm run verify:vocabulary-preview-acquisition`；若修改获取服务，复用 HOST-01 相应检查。无代码修改则不重复跑构建。

交接标注“已复现并修复”或“本轮未复现，未改代码”，不要用“未复现”替代历史问题的解决证明。

## 5. HOST-03：一次正常入口使用确认

### 目标和验收口径

验证用户实际用得上的两件事：复习能保存，预习能进入并恢复。真实结果与模拟结果分开记录，结束本次维修，不再接 H3→H4→H5。

### 顺序步骤

1. 用当前优化启动器 `scripts/launch-optimization-preview.ps1` 启动所需实例。先确认已有实例和实际配置，不同时开第二个写入者，不修改受保护工作区。开发调试使用其明确支持的方式，不修改固定配置去迎合旧测试脚本。
2. 如果启动失败，只依据当次错误处理直接原因，例如缺失依赖、失效路径、已知实例残留或代理目标错误。未知进程占端口时说明进程身份，不直接杀进程。不引入“连续健康 N 秒才允许测试”的新前置条件。
3. 在隔离浏览器及合成内容上，从正常主入口进入 SRS：揭示一张卡并评分，确认进入下一张；对另一张卡快速重复输入一次，确认只记一笔。刷新后读回评分记录。两张卡足够，不要求四档延迟矩阵。
4. 打开预习，揭示一个词并前进一步；关闭重开和刷新后确认进度仍在。引用 HOST-02 已经完成且未受后续修改影响的相同证据，不重复做同一路径。
5. 对本轮代码运行一次 `npm run build` 和 `git diff --check`，引用已完成的关联检查。只有确实改了启动器，才补对应启动／停止测试；没有启动器修改不要求清空所有旧 launcher 检查。
6. 停止本任务启动的临时服务，记录合成数据位置及处理结果；不删除既有用户记录或旧实验根。

若正常入口仍被新报错阻断，交接准确的入口、操作和错误，按一个明确的小问题处理；不要重跑整套验收去碰运气。沿用 AGENTS.md 的两轮修复失败后重新评估规则，不增加其他门禁。

### 收口交付

- 实际修复了哪一种 Host 问题、涉及哪些文件。
- 哪些检查使用了真实 Python 存储，哪些走了真实 HTTP／浏览器，哪些是模拟。
- 正常复习保存／预习恢复的结果，尚未复现或仍存在的问题。
- 提交由用户决定，不自动提交无关差异。

仅当实际入口验证也通过，才写“本次 Host 保存与入口维修完成”。只有 HOST-01 通过则写“版本竞争修复通过，正常入口待确认”。历史严格延迟门槛、全六域、跨机器、长期健康采样和旧测试数据恢复均不作为本轮完成条件。
