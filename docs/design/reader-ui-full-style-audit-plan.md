## 1. 目标、范围和最终回答

用户需要知道：整个当前应用究竟哪些元素已经统一为现有 Tailwind + shadcn-vue 外观，哪些仍由旧的或专用 CSS 控制，以及哪些属于遗漏或覆盖问题。

本次是全应用样式调查，不是继续施工。一个检查对话连续完成盘点、浏览器检查、来源分析及报告；不要每查一个页面就停下来请求确认，也不要自动创建任务或代理。遇到受阻对象记录原因，继续能独立完成的部分，最终如实报告缺口。

范围包括当前可达的页面、工具栏、弹窗、浮层、菜单、内容 tab、折叠子项、条件提示及其内部可见元素。用户的六张截图只是疑点线索，旧 UI-001 至 UI-028 只是历史索引，U01–U10 只是旧分组；三者均不是本轮上限。不能预填当前界面总数。

两个问题必须分开回答：

1. 原施工方案的约定是否真正落实，有没有漏改、错误覆盖或具体功能退化。
2. 整个应用的外观是否已经统一；即使原方案允许保留，也要列出仍保留独立外观的元素。

“旧方案允许保留”不能等价于“已完成视觉统一”；“使用原生 HTML 节点”也不能等价于“未使用共享配方”。所有控件最终都要渲染为 DOM，应检查样式实现及最终获胜规则。

### 4.1 从实际入口向内追踪

### 4.3 从样式反查消费者

检查根 CSS、功能 CSS、Vue scoped/style 块、内联 style、JS 注入样式、运行时 class 切换及变量设置，反查其当前消费者。

重点查 `!important`、未分层规则、旧 id/全局 button/input 选择器、圆角/阴影/渐变/模糊、硬编码颜色、固定宽高与 padding、伪元素、选中/等待/错误类。源码有规则但暂未找到消费者的，单列待确认，不自动认定可删除。

2. 主标题、副标题、标签、辅助文字、单位、空态说明及图标。
3. 普通/图标/危险按钮、文本/密码/数字输入、Textarea。
4. tab/筛选组/开关、checkbox/radio/select、折叠 summary（实际存在才列）。
5. badge、计数、记录行、候选行、进度/步骤卡、状态提示。
6. 快捷键录制卡、kbd、媒体/颜色/文件输入、正文专用交互。
7. hover/focus/disabled/selected/pending/error 等状态样式及 ::before/::after。

同样的元素重复十次不必测十次，但必须列出重复实例/选择器覆盖范围。只有配方、ancestor、owner、外观覆盖和状态逻辑相同才能合并。不同弹窗中的同类按钮仍分别检查上下文；不能因为共用 Button 就跳过。

例外按属性判断：自动高度的例外不自动允许不同圆角、padding 和文字色；保留行布局不自动允许残留玻璃装饰；语义状态色不自动允许整张普通卡沿用旧品牌色。

## 7. 实现方式与调查结论分别分类

### 7.1 实现方式（客观事实）

| 编号 | 含义 |
| --- | --- |
| M1 | 实际 Vue 共享组件，例如 Button/Input/Textarea |
| M2 | 原生节点使用相同配方或 native 样式助手 |
| M3 | 专用 CSS/内联/运行时样式；可能使用共享 token，也可能硬编码 |
| M4 | 浏览器/OS 原生外观与选择界面 |

一个元素可以 M1+M3 或 M2+M3；必须标出 M3 改了哪些属性。不要将 M1/M2 自动算为外观已统一。当前项目是否有 Dialog/Badge/Tabs 等共享组件需现场确认，没有这些组件不能凭外观认定“已迁移到该组件”。

### 7.2 每个元素的最终状态

| 编号 | 状态 | 必要依据 |
| --- | --- | --- |
| S1 | 已接入且最终样式符合共享基准 | 当前 DOM、实际生效属性及配方对照 |
| S2 | 原方案明确保留的专用/原生外观 | 明确条款及逐属性保留范围；仍计入未统一外观清单 |
| S3 | 原方案范围内漏改或被旧规则覆盖 | 条款、真实消费者、获胜规则、可复现差异 |
| S4 | 尚未统一，属于新增统一建议或原方案未明确要求 | 记录视觉差异与实现来源，不冒充原验收失败 |
| S5 | 未验证或受阻 | 已尝试路径、缺少条件、最小补充方式 |

布局规则与装饰规则分开标注。保留必要定位/滚动/网格不等于保留全部旧外观。对原方案确实含糊的项目使用 S4 并解释，不能自由扩大“有限例外”。

## 8. 浏览器检查步骤与状态矩阵

### 8.1 每个界面都执行的步骤

1. 按清单的入口路径打开实际应用容器，记录前置合成数据及所属路由。主阅读器与独立 SRS 均需取得实际产品页面。
2. 为该容器取得一张不含私人数据的全貌截图，核对标题、正文及入口未错页。长列表/长弹窗滚动检查底部，不只截首屏。
3. 枚举当前适用元素组，采集默认态 DOM 和 computed style，再追踪关键属性的最终来源。
4. 逐个打开独立子项/菜单/折叠区域。对内容不同的子项保留独立记录；同一容器浅深主题作为状态，不算新页面。
5. 触发适用的状态，确认事件、焦点和选中状态确实发生；不以设置一个 CSS class 冒充实际业务交互。
6. 核对窄屏、关闭与返回焦点。记录结果并更新未验证清单，再进入下一对象。

### 8.2 最小矩阵

- 每个当前可达视觉容器及不同子视图至少真实打开一次。保留项同样需要记录，不因为原表写“保留”而跳过。
- 视口默认 1280×800 与 390×844。每个独立容器检查这两种宽度；同布局的子项可复用尺寸测量，但有长文案、独立 footer 或不同列数的子项必须单独核对。
- 正常浅色为无 data-theme 的默认路径；主题敏感容器检查深色。学习窗口检查深色 reader 下仍为固定浅色；独立 SRS 单独核对。
- custom 至少检查 reader 主壳、主题编辑和依赖 reader token 的表面；正文自定义色不能被普通 UI token 意外重置。
- 每个独特的规则/元素族检查 hover、键盘 focus-visible、disabled、selected、pending、错误中适用的状态。无需对全部元素执行所有状态的笛卡尔积。
- 数据状态用最小合成集覆盖空态、有数据、长名称、多条记录、失败及 pending。素材历史至少两次尝试；预习至少两词；SRS 至少两卡以检查揭示/评分切换；owner 不可用和组件加载失败使用模拟。
- 浏览器自动填充、原生 focus、系统控件是独立来源。截图中出现蓝底或厚边框时，先区分 autofill/浏览器状态、共享 focus ring 和遗留覆盖，不凭颜色猜原因。

### 8.3 每个关键元素测量什么

- 几何：box-sizing、width/height/min/max、padding、gap、line-height、字体大小/粗细、圆角、图标宽高。
- 外观：前景/背景、边框、阴影、opacity、滤镜、伪元素及其继承 token。
- 控制来源：class、owner、scope、stylesheet/source file、selector、layer、!important、变量定义和运行时覆盖。computed style 只给值，必须结合匹配规则/源码定位确认来源。
- 可用性：文案裁切、横向溢出、点击目标覆盖、滚动到底可见性、focus-visible、disabled 是否仍可触发；不用 UI 检查声称完整无障碍认证。

按钮不能只测 h-9：必须检查 padding、gap、圆角、边框、字体及 SVG 自动尺寸。图标有显式 size 时按原配方规则保留。输入保留 type、number/trim/IME 语义；视觉检查不能修改字段类型取得统一。

## 9. CSS 遗留调查与生产一致性

把仍然生效的 CSS 分为：必要布局、专用语义/内容、共享 token 映射、普通控件覆盖、旧装饰、疑似无消费者。每项关联消费者与状态。

对普通控件覆盖及旧装饰，至少回答：哪个声明最终获胜；来自哪个文件/层/选择器；影响哪些页面；是否符合原方案例外；需要保留的是整个规则还是部分属性。不会删除任何 CSS，只提出最小处理建议。

CSS Coverage、匹配数和扫描行数只能辅助发现。规则被划掉不代表整个规则无用；首页没命中不代表动态页面不用；文件变短不代表清理正确。

生产检查要求：

1. 分别读取 reader 与 standalone SRS 的实际样式加载顺序，包括异步功能 CSS。不能假设两个入口的层顺序相同。
2. 检查 reader-footprint、properties、theme、base、components、utilities 的实际建立顺序；同时检查非分层规则、scoped 规则和 !important。
3. 将每一种已发现的覆盖模式，以及每个独立样式上下文中的代表控件，用当前生产 CSS 复核。包括 reader/workflow/style-controls/learning、原生助手控件、图标及 teleported 表面。
4. 本轮发现疑点的容器必须检查对应生产表现；不能仅用单个按钮样本为全部生产页面背书。

## 12. 完成条件与报告格式

完成条件：

- 三条发现路径中的候选项全部有清单去向，未归类入口为零；不声称穷尽未来功能或所有理论错误码。
- 已发现当前界面的适用元素组均有 S1–S5 结论，不能用“其他相似”省略整页。
- S3/S4/S5 分别列清，明确保留的旧外观也可被用户查看。
- 未验证项不能写成“不适用”或“历史不可达”。存在必要打开/来源/生产证据缺口时，报告部分完成及最小补充项。
- 不以发现第一个问题、六张图查完、28 项打勾或一个服务受阻为提前结束条件。
- 不自动进入修复循环；若后续安排修复，遵守项目已有两次连续修复/复审失败停止规则，不在这里设计扩大化门槛。

最终报告按下面顺序输出：

1. 直接回答：目前是否全部统一；实现仍有哪些混合方式；不预设答案。
2. 检查完成度：完成/部分完成，当前 HEAD 与浏览器/产物身份，未检查/受阻范围。
3. 实际盘点：产品容器数、不同子视图数、元素组数、各 S 分类数量；历史/演示项另列。不要把观察状态数当界面数；未定义分母时不报“替换率”。
4. 原范围真实缺陷清单；按严重程度写入口、实际结果、标准、文件行号与最小处理方向。
5. 明确保留的旧外观清单，以及新增统一建议；说明是否只改样式即可，还是需要替换组件及验证交互。
6. 未验证清单和最小补充证据；不得用一句“整体 PASS”掩盖。
7. C01–C08 表、界面及元素明细、关键证据路径。长表可以分段，但不能省略检查对象。

即使原方案 A01–A10 仍全部通过，只要 S2/S4 中仍有自定义外观，也应明确说明“原范围符合，但尚未全应用统一”。调查完成与产品完全统一是两个结论。
